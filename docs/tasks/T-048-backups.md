# T-048: Бэкапы Postgres

**Фаза:** 5 · **Оценка:** 3ч · **Зависит от:** T-047 · **Статус:** todo

## Цель
Ежедневный дамп обеих БД уходит в S3; восстановление проверено руками.

## Контекст
[08-infrastructure.md](../08-infrastructure.md#бэкапы): pg_dump -Fc в 03:00 МСК, хранение
30 дней (lifecycle-политика бакета orbital-backups).

## Что сделать
- [ ] `/opt/orbital/backup.sh`: `docker compose exec -T postgres pg_dump -Fc -U orbital orbital` → файл `{stack}-YYYY-MM-DD.dump` → `aws s3 cp` (aws-cli в отдельном контейнере или на хосте); для обоих стеков
- [ ] cron (`crontab -e` от deploy): `0 3 * * * /opt/orbital/backup.sh >> /var/log/orbital-backup.log 2>&1`
- [ ] Lifecycle-политика бакета: expire 30 дней
- [ ] Проверка восстановления: скачать дамп → `pg_restore` в пустую БД staging-Postgres → приложение staging работает на восстановленных данных
- [ ] Записать процедуру восстановления в этот файл (точные команды)

## Затрагиваемые файлы
- VPS: /opt/orbital/backup.sh, crontab

## Критерии приёмки
- [ ] После ручного запуска backup.sh дампы лежат в S3
- [ ] Восстановление из дампа прошло, данные на месте
- [ ] Через сутки — автоматический дамп появился сам

## Как проверить
`./backup.sh` → S3-консоль → pg_restore-прогон по записанной процедуре.

## Подводные камни
`-T` флаг у exec обязателен в скрипте (нет TTY в cron). Дамп содержит ПД — бакет приватный,
ключи только на VPS. Ежемесячное повторение проверки — в календарь.
