# ADR-0007: Стратегия soft-delete

**Статус:** принято · **Дата:** 2026-07-30

## Контекст
Часть данных пользователь удаляет из UI; ошибка удаления кандидата или диалога болезненна.
Финансовые записи и кампании — быстро правятся и переносимы. Платежи — финансовый след,
удалять нельзя никогда. Аккаунт — нужно окно передумать.

## Решение
`deletedAt DateTime?`:
- **Soft-delete:** Specialist, Request (каскадно soft-delete'ит своих специалистов),
  Conversation, OpsTask, Company (окно 30 дней, затем hard-каскад + чистка S3 джобом).
- **Hard-delete:** FinanceRecord, Campaign (низкая ценность, легко пересоздать).
- **Никогда не удаляются:** Payment, AnalyticsEvent, StatusChange.

Репозитории фильтруют `deletedAt: null` по умолчанию; уникальность `Conversation.specialistId`
не конфликтует, т.к. специалист удаляется вместе с диалогом.

## Альтернативы
- **Всё hard** — проще, но безвозвратная потеря переписки/кандидатов от одного мисклика.
- **Всё soft** — таблицы-кладбища и вечные фильтры там, где это не нужно.
- **Отдельная archive-таблица** — сложность без выгоды на нашем объёме.

## Последствия
- (+) Восстановление специалистов/диалогов тривиально (UPDATE deletedAt=NULL, admin-функция).
- (−) Каждый запрос обязан фильтровать deletedAt — закреплено сигнатурами репозиториев и тестом
  «удалённое не видно в списках/чате/поиске».
- Job очистки компаний (30 дней) — единственный фоновый процесс v1 (node-cron внутри API).
